# 対応要件

## 1. 目的

本対応では、既存システムに対する機能追加・仕様変更に伴い、関連するソースコード、DB、IF、画面、OL機能、BT機能等への影響を調査する。

Claude Codeは、本要件書の内容を基準として既存プロジェクトを調査し、

1. 影響範囲を特定する
2. 影響箇所と影響理由を整理する
3. 既存処理との関連・呼出関係を明確にする
4. 改修が必要な箇所を特定する
5. 改修方針を作成する
6. 調査結果をMarkdown形式の報告書として出力する

こと。

# 3. 影響調査方針

## 3.1 基本方針

影響調査は、単純なキーワード検索だけで判断しないこと。

以下の順番で調査すること。

1. 要件から変更対象を明確化する
2. 関連するDB・テーブル・項目を特定する
3. 関連するIFを特定する
4. 関連する画面を特定する
5. 関連するOL機能を特定する
6. 関連するBT機能を特定する
7. ソースコード上の参照・更新箇所を特定する
8. 呼出元・呼出先を確認する
9. データの流れを確認する
10. 共通処理への影響を確認する
11. テストコードへの影響を確認する
12. 改修要否を判断する

# 5. 呼出関係の調査

影響調査では、対象処理だけを確認して終了してはいけない。

最低限、以下を確認すること。

### 5.1 呼出元

対象メソッド・クラスを呼び出している処理を確認する。

### 5.2 呼出先

対象メソッド・クラスが呼び出している処理を確認する。

### 5.3 データの流れ

対象データが、

`入力 → Validation → Business Logic → DB/IF → 出力`

のどの経路を通るか確認する。

### 5.4 間接影響

直接参照していない場合でも、

* 共通処理
* 親クラス
* 継承
* Interface
* 共通SQL
* 共通DTO
* 共通Mapper
* 設定ファイル

を経由した影響がないか確認する。

---

# 6. 影響判定ルール

各調査対象について、以下のいずれかを判定する。

### 影響あり

今回の要件変更によって、ソースコード・DB・IF・画面・処理仕様等の変更が必要になる場合。

### 影響なし

関連性は確認できるが、今回の要件変更による変更は不要な場合。

### 要確認

ソースコード・設計書・設定等から明確に判断できず、人による確認が必要な場合。

「影響あり」と判断した場合は、必ずその理由を記載すること。

---

# 7. 改修方針

影響調査後、改修対象について改修方針を作成する。

単に、

「〇〇.javaを修正する」

という記載は禁止する。

以下を明確にすること。

1. どのファイルを変更するか
2. どのクラス・メソッドを変更するか
3. なぜ変更する必要があるか
4. 現在どのような処理になっているか
5. 変更後どうするか
6. 他処理への影響はあるか
7. テストで何を確認するか

---

# 10. Claude Codeへの重要な調査ルール

以下を必ず守ること。

### ルール1：推測禁止

ソースコードから確認できない内容を事実として記載しない。

判断できない場合は、

`要確認`

として記載する。

### ルール2：検索結果の羅列禁止

単純なgrep結果を並べるだけではなく、

「なぜ影響するのか」

まで説明すること。

### ルール3：呼出関係を確認する

対象ファイルだけでなく、

* 呼出元
* 呼出先
* DB
* IF
* 画面
* Batch
* 共通処理

まで追跡すること。

### ルール4：影響なしも理由を書く

「影響なし」とだけ記載してはいけない。

必ず、

`なぜ影響なしなのか`

を説明する。

### ルール5：既存仕様を尊重する

今回の要件に不要な既存処理の変更は提案しない。

### ルール6：最小改修を基本とする

既存設計・既存アーキテクチャを可能な限り維持し、必要最小限の改修を基本方針とする。

### ルール7：設計書とソースコードに差異がある場合

設計書とソースコードの内容が一致しない場合は、その差異を明記する。

例：

`設計書ではXXXとなっているが、実装ではYYYとなっている。`

### ルール8：根拠を残す

調査結果には可能な限り、

* ファイルパス
* クラス名
* メソッド名
* SQL
* 行番号

を記載する。

以下のプログラムを、初めて読むエンジニアが全体像をつかめるように解説してください。

# 解説のルール

- 変数名・関数名は、必ず実際のコードに出てくる名前をそのまま使うこと。
  勝手に一般的な名前（`data`, `func1` など）に置き換えない。
- ただし、その名前が何を表しているかを補足し、可読性の高い説明を添えること。
  （例：`usrCnt` → ユーザー数を保持するカウンタ）
- 関数の呼び出し関係・ジャンプ（条件分岐、ループ、再帰、goto、コールバック、
  イベントハンドラ、非同期処理など）の構造が追えるように説明すること。
- 「どこから呼ばれ、どこへ処理が移り、どこへ戻るか」を意識して書くこと。
- 専門用語を使う場合は、簡単な補足を付けること。

# 出力フォーマット

## 1. 機能概要（何をするプログラムか）
- このプログラムが「何を実現するものか」を 3〜6 行で要約。
- 入力・出力・主な用途を明示。

## 2. 全体構成（大きなブロック分け）
- プログラムを意味のある塊（モジュール／関数群／処理フェーズ）に分ける。
- 各ブロックの役割を 1〜2 行で説明。
- 可能なら、ブロック間の呼び出し関係をテキスト図で示す。
  （例：`main()` → `parseArgs()` → `runTask()` → `saveResult()`）

## 3. 処理の流れ（どうやって実現しているか）
- 実行順に沿って、どの関数がどの関数を呼び、どこで分岐・ループ・ジャンプするかを説明。
- 各ステップで「何が起きるか」を具体的に。
- 再帰やコールバックがある場合は、その流れを明示。

## 4. データフロー（どんなデータがどう処理されるか）
- 主要なデータ（変数・引数・戻り値・構造体・ファイル・通信データなど）ごとに、
  以下を追跡して説明：
  - どこで生成されるか
  - どんな型・形か
  - どこで変更されるか
  - どこへ渡され、どう使われるか
  - 最終的にどこへ出力・保存されるか
- 実際の変数名を使って、「A → B → C」のように流れを書く。
- 表形式にすると分かりやすい場合は表を使う。

## 5. 注意点
- バグの可能性、エッジケース、例外処理の抜け、リソース管理の問題など。
- 読み手が誤解しやすい箇所。

## 6. 改善提案
- 可読性・保守性・性能・安全性の観点で改善案を提示。
- 優先度（高・中・低）を付ける。
- 可能なら具体的な修正方針やコード例を示す。
