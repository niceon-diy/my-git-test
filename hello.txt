# 対応要件

## 1. 目的

本対応では、既存システムに対する機能追加・仕様変更に伴い、関連するソースコード、DB、IF、画面、OL機能、BT機能等への影響を調査する。

Claude Codeは、本要件書の内容を基準として既存プロジェクトを調査し、

1. 影響範囲を特定する
2. 影響箇所と影響理由を整理する
3. 既存処理との関連・呼出関係を明確にする
4. 改修が必要な箇所を特定する
5. 改修方針を作成する
6. 調査結果をMarkdown形式の報告書として出力する

こと。

# 3. 影響調査方針

## 3.1 基本方針

影響調査は、単純なキーワード検索だけで判断しないこと。

以下の順番で調査すること。

1. 要件から変更対象を明確化する
2. 関連するDB・テーブル・項目を特定する
3. 関連するIFを特定する
4. 関連する画面を特定する
5. 関連するOL機能を特定する
6. 関連するBT機能を特定する
7. ソースコード上の参照・更新箇所を特定する
8. 呼出元・呼出先を確認する
9. データの流れを確認する
10. 共通処理への影響を確認する
11. テストコードへの影響を確認する
12. 改修要否を判断する

# 5. 呼出関係の調査

影響調査では、対象処理だけを確認して終了してはいけない。

最低限、以下を確認すること。

### 5.1 呼出元

対象メソッド・クラスを呼び出している処理を確認する。

### 5.2 呼出先

対象メソッド・クラスが呼び出している処理を確認する。

### 5.3 データの流れ

対象データが、

`入力 → Validation → Business Logic → DB/IF → 出力`

のどの経路を通るか確認する。

### 5.4 間接影響

直接参照していない場合でも、

* 共通処理
* 親クラス
* 継承
* Interface
* 共通SQL
* 共通DTO
* 共通Mapper
* 設定ファイル

を経由した影響がないか確認する。

---

# 6. 影響判定ルール

各調査対象について、以下のいずれかを判定する。

### 影響あり

今回の要件変更によって、ソースコード・DB・IF・画面・処理仕様等の変更が必要になる場合。

### 影響なし

関連性は確認できるが、今回の要件変更による変更は不要な場合。

### 要確認

ソースコード・設計書・設定等から明確に判断できず、人による確認が必要な場合。

「影響あり」と判断した場合は、必ずその理由を記載すること。

---

# 7. 改修方針

影響調査後、改修対象について改修方針を作成する。

単に、

「〇〇.javaを修正する」

という記載は禁止する。

以下を明確にすること。

1. どのファイルを変更するか
2. どのクラス・メソッドを変更するか
3. なぜ変更する必要があるか
4. 現在どのような処理になっているか
5. 変更後どうするか
6. 他処理への影響はあるか
7. テストで何を確認するか

# 10. Claude Codeへの重要な調査ルール

以下を必ず守ること。

### ルール1：推測禁止

ソースコードから確認できない内容を事実として記載しない。

判断できない場合は、

`要確認`

として記載する。

### ルール2：検索結果の羅列禁止

単純なgrep結果を並べるだけではなく、

「なぜ影響するのか」

まで説明すること。

### ルール3：呼出関係を確認する

対象ファイルだけでなく、

* 呼出元
* 呼出先
* DB
* IF
* 画面
* Batch
* 共通処理

まで追跡すること。

### ルール4：影響なしも理由を書く

「影響なし」とだけ記載してはいけない。

必ず、

`なぜ影響なしなのか`

を説明する。

### ルール5：既存仕様を尊重する

今回の要件に不要な既存処理の変更は提案しない。

### ルール6：最小改修を基本とする

既存設計・既存アーキテクチャを可能な限り維持し、必要最小限の改修を基本方針とする。

### ルール7：設計書とソースコードに差異がある場合

設計書とソースコードの内容が一致しない場合は、その差異を明記する。

例：

`設計書ではXXXとなっているが、実装ではYYYとなっている。`

### ルール8：根拠を残す

調査結果には可能な限り、

* ファイルパス
* クラス名
* メソッド名
* SQL
* 行番号

を記載する。

# 対象プログラムの前提

- 言語：COBOL
- バージョン：COBOL（使用されている構文・方言が判別できる場合は明記。判別不能なら
  「標準 COBOL 相当」として扱う）
- 図の粒度：**関数（段落・SECTION・PERFORM 対象）単位**。1 ブロック＝1 段落/SECTION。
- 想定読者：**COBOL 初学者**。専門用語には必ず短い補足を付ける。
- 特に注視する観点：
  1. **制御フラグの挙動**（スイッチ変数・状態変数が true/false・状態値によって
     処理がどう分岐するか）
  2. **関数呼び出しチェーン**（PERFORM / CALL / GO TO による呼び出し関係と戻り先）

# 最終成果物の形式

- 出力は **単一の HTML ファイル**（外部 CDN・外部 CSS・外部 JS に依存しない。
  必要な CSS/JS はすべて `<style>` / `<script>` 内に埋め込む）。
- ブラウザで開くだけで動くこと。ビルド不要。
- その HTML の中に、以下をすべて含める：
  1. 解説本文（日本語）
  2. プログラム本体のソースコード（整形・行番号付き・ハイライト付き）
  3. 処理フロー／データフローの可視化図（SVG または HTML+CSS で描画）
  4. 図とコードを行き来できるジャンプ機能
  5. 制御フラグ一覧と関数呼び出しチェーン図

# COBOL 初学者向けの配慮

- COBOL 特有の構造を初学者向けに噛み砕いて説明する：
  - `IDENTIFICATION DIVISION` / `ENVIRONMENT DIVISION` / `DATA DIVISION` /
    `PROCEDURE DIVISION` の役割
  - `WORKING-STORAGE SECTION`（作業用変数の置き場）
  - `PIC` 句（例：`PIC 9(3)`、`PIC X(10)`）が「どんな形・桁数のデータか」を表すこと
  - `PERFORM`（段落や SECTION を呼び出して実行する）、`PERFORM ... THRU`、
    `PERFORM UNTIL`、`PERFORM VARYING` の違い
  - `CALL`（外部プログラム呼び出し）と `GO TO`（無条件ジャンプ）の違い
  - レベル番号（01, 05, 77, 88 など）の意味。特に **88 レベル条件名**は
    制御フラグとして重要なので丁寧に扱う。
  - `MOVE` / `COMPUTE` / `ADD` / `IF` / `EVALUATE` の基本動作
- 専門用語（例：レベル番号、PIC 句、88 レベル、PERFORM、GO TO）は
  初出時に 1 行でよいので補足を付ける。

# 必須要件

## A. コード表示
- プログラム全体を 1 つのコードブロックとして表示する。
- **各行に一意な ID を付与**する（例：`id="L42"`）。
- 行番号を表示する（COBOL の列番号に注意。7 桁目以降が本文である点も補足）。
- 構文ハイライトを付ける（自前実装でよい）。
- 変数名・段落名・SECTION 名は**実際のコード上の名前をそのまま**使う。
  勝手に一般的な名前に置き換えない。
- 各段落 / SECTION にアンカーを持たせ、URL ハッシュでもジャンプできるようにする。

## B. フローチャート／データフロー図
- 処理の流れを **ブロック図**で可視化する。
- **1 ブロック＝1 段落 / 1 SECTION（関数単位）**とする。
- 各ブロックは以下を区別して描き分ける：
  - 開始 / 終了（端子）
  - 通常処理
  - 条件分岐（IF / EVALUATE）
  - ループ（PERFORM UNTIL / PERFORM VARYING）
  - 段落・SECTION 呼び出し（PERFORM）
  - 外部プログラム呼び出し（CALL）
  - 無条件ジャンプ（GO TO）※初学者が誤解しやすいので目立たせる
  - 入出力（ACCEPT / DISPLAY / ファイル入出力）
  - エラー処理
- データの流れを **矢印付きのエッジ**で示す。
  - 処理の流れ（control flow）とデータの流れ（data flow）は
    色・線種を変えて区別する（例：実線＝制御、破線＝データ）。
- 各ブロックに、対応する**コードの行番号範囲**を表示する。
- **ブロックをクリックすると、対応するコード行へスクロールしてハイライト**する。
- 逆に、コード行をクリックすると対応するブロックがハイライトされる（双方向）。
- データフローは「どの変数（実名）が、どこで生成され、どこで変更され、
  どこへ渡るか」を追えるようにする。

## C. 制御フラグの明示（重点観点 1）
- プログラム中の**重要な制御用フラグ**をすべて洗い出し、以下を明示する：
  - 変数名（実名）
  - **88 レベル条件名**を使っている場合は、その条件名と親変数の関係
  - 役割（何を制御しているか）
  - 初期値（VALUE 句があればそれも）
  - 変化する箇所（行番号）
  - 参照される箇所（行番号）
  - 値ごと（true/false、または各状態値）で処理がどう変わるか
- 専用セクション「制御フラグ一覧」に表形式でまとめる。
- コード上でも、フラグ変数・88 レベル条件名は目立つ色でハイライトする。
- フローチャート上でも、フラグによる分岐は特別なマーク（例：★や色）を付ける。

## D. 関数呼び出しチェーン（重点観点 2）
- **PERFORM / CALL / GO TO による呼び出し関係**を可視化する。
- 専用セクション「呼び出しチェーン図」を用意する。
  - 例：`MAIN-PROCESS` → `PERFORM INIT-PARA` → `PERFORM READ-LOOP` →
    `PERFORM CHECK-FLAG` のように、呼び出し元 → 呼び出し先を矢印で示す。
  - `PERFORM ... THRU` の場合は範囲を明示。
  - `CALL` は外部プログラムとして別色で示す。
  - `GO TO` は「戻らないジャンプ」であることを明示し、初学者が混乱しないよう
    「通常の呼び出しとどう違うか」を注記する。
- 呼び出しチェーン図の各ノードも、クリックでコードへジャンプできるようにする。

## E. 解説本文の構成（この順序で）
1. **機能概要**：何をするプログラムか（3〜6 行）。COBOL 初学者向けに平易に。
2. **全体構成**：4 つの DIVISION の役割と、段落 / SECTION の塊ごとの役割。
3. **処理の流れ**：実行順に沿って、PERFORM / CALL / GO TO の流れを追う。
   ループ（PERFORM UNTIL / VARYING）と分岐（IF / EVALUATE）を明示。
4. **データフロー**：主要データ（実名）ごとに「生成 → 変更 → 受渡し → 出力」を追跡。
   PIC 句の意味も添える。
5. **制御フラグ一覧**：C の表。
6. **呼び出しチェーン図**：D の図。
7. **注意点**：バグ可能性、エッジケース、例外処理の抜け、GO TO の多用による
   可読性低下、リソース管理、初学者が誤解しやすい点。
8. **改善提案**：可読性・保守性・性能・安全性の観点。優先度（高/中/低）付き。
   COBOL らしい改善（例：GO TO を PERFORM に置き換える、88 レベル条件名を活用する）
   も提案する。

## F. 可読性・UI
- レイアウトは「左：解説＋図」「右：コード」または
  「上部：図」「下部：コード＋解説」など、見やすければ自由。
- 図とコードが同時に見える、またはワンクリックで切り替わる構成にする。
- ダークモードでも読める配色にする（または切り替えボタンを付ける）。
- クリック可能な要素はホバーで分かるようにする。
- ジャンプ時はスムーズスクロール＋一時ハイライト。

## G. 出力の制約
- 説明文・ラベル・コメントはすべて**日本語**。
- 変数名・段落名・SECTION 名はコード上の実名を保持。
- 外部ライブラリ禁止（Mermaid 等も使わない。SVG/CSS/JS で自前描画）。
- 単一ファイルで完結。ファイル名例：`cobol_program_explainer.html`。
